# 10. 결제(Payment)
- 우리나라 기준으로 결제는 PG사 연동 API를 통해 처리하게 된다.
- 외부랑 소통하는 경우 외부의 문제 -> Timeout, 결제 Fail, 한도초과, 잔액부족 -> 전부 실패로 떨어짐
- 실패한 주문에 대해서 다시 결제가 가능하도록 만들건지
- 주문 -> 결제로 간단하지 않고 생각하지못한 케이스에 대해서 어떻게 처리할 지 고민해야됨
- 실패한 케이스 기록, 결제 실패 이력 기록해야되는지?

## 결제 과정
1. 주문에서 결제창으로 넘어간다.
2. 결제 대행사에서 결제 처리를 한다.
3. 결제가 성공하거나 실패하는 케이스가 callback으로 들어온다.

## 결제 도메인 분석
- 금액과 관련된 부분이기 때문에 엄격한 관리와 검증이 필요하다.
- 결제는 성공과 실패로 나뉘고 실패에서는 여러 케이스가 존재한다.
- 케이스 별로 다른 처리가 필요하다.

## 토스 페이먼츠의 PG 결제 흐름 문서 분석
커머스 서비스의 결제 부분을 구현하기 위해서 PG사의 결제 흐름을 분석하는 것이 중요하다고 생각했다.
현재 우리 서비스는 다음과 같은 흐름을 가진다.
장바구니에 상품 담기 -> 담은 상품들을 토대로 주문 생성 -> 주문서 기준 쿠폰과 포인트를 적용하고 최종 가격으로 결제 요청
위와 같은 순서를 거쳐서 결제로 이동하게 된다.
최종 가격 -> 결제 요청 순서로 진행된다.

### 결제 실패 케이스
- Timeout(Timeout에도 여러가지 케이스가 존재함)
- 결제 Fail
- 한도 초과
- 잔액 부족

### 결제 프로세스
- 주문 생성 후 결제 페이지로 이동
- PG사에서 결제 처리 실행
- 결제 성공 및 실패 여부를 callback으로 수신
- 결제 요청 이전에 결제를 PaymentRepository에 생성 후 Status를 PENDING, SUCCESS로 나눔

### 결제 흐름 정리
**1단계: Payment 엔티티 생성**  
주문 생성 후 결제를 위한 Payment 엔티티를 PaymentRepository에 생성
초기 상태: PENDING
OrderKey를 통해 주문과 결제 내역 연결

**2단계: PG사 결제 요청**  
PENDING 상태의 Payment를 기반으로 PG사에 결제 요청 송신
결제 페이지로 사용자 이동

**3단계: Callback을 통한 상태 업데이트**  
PG사로부터 결제 결과 수신
- 결제 성공: Payment 상태를 SUCCESS로 변경
- 결제 실패: Payment 상태를 FAIL로 변경

### 결제(Payment) 테이블 정의
- id
- orderId: order FK
- userId: 결제 요청자 ID
- paymentStatus: 결제 상태(PENDING, SUCCESS, FAIL)
- totalAmount: 결제 총 금액
- paymentMethod: 결제 수단
- transactionId: PG사에서 발급하는 거래 고유 ID
- failureCode, failureReason: 실패 코드와 실패 사유

## 유스케이스 시나리오
### PAYMENT-UC-001-01: 주문창에서 결제 클릭시 결제 플로우 이후 결제 성공
1. 사용자가 주문 페이지에서 결제 버튼(Go to Payment) 클릭
2. 백엔드에서 Payment 엔티티 생성 (상태: PENDING)
3. PG사 결제 페이지로 사용자 리다이렉트
4. 사용자가 원하는 지불 방식 선택 후 결제 인증 완료
5. PG사에서 결제 완료 callback 수신
6. 백엔드에서 PG사 API를 통해 결제 검증
7. Payment 상태를 SUCCESS로 변경
8. 주문 상태를 PAYMENT_SUCCESS로 변경
9. 사용자에게 결제 완료 페이지 표시

### PAYMENT-UC-001-02: 주문창에서 결제 클릭시 결제 플로우 중 결제 실패
1. 사용자가 주문 페이지에서 결제 버튼(Go to Payment) 클릭
2. 백엔드에서 Payment 엔티티 생성 (상태: PENDING)
3. PG사 결제 페이지로 사용자 리다이렉트
4. 사용자가 지불 방식 선택 후 결제 시도
5. 결제 도중 문제 발생 (한도초과, 잔액부족, 유효하지 않은 카드 등)
6. PG사에서 결제 실패 callback 수신
7. 백엔드에서 PG사 API를 통해 결제 상태 검증
8. Payment 상태를 FAIL로 변경
9. failureCode와 failureReason 저장
10. 주문 상태를 PAYMENT_FAILED로 변경
11. 사용자에게 결제 실패 페이지 표시 및 재결제 옵션 제공

## 구현 고민 및 해결법
- TransactionId는 nullable 해야 하는가?
  - nullable 해야한다. 생성 시점에 transactionId를 생성하면 안전하지만, 반대로 아예 PG사와 통신 자체가 안되면 transactionId는 생성 되지 않기 때문에 DB Insert가 되지 않음
